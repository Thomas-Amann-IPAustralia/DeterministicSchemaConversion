# DeterministicSchemaConversion — File Reference Report

## Current Core Workflow

```
SCRAPE (Stage 1)  →  MD→JSON (Stage 2)  →  JSON→CSV (Stage 5)
scraper.py            process_md_to_json.py    json_to_csv.py
scrape.yml            process_json.yml          stage5_normalization.yml
```

Everything outside these three stages is either supporting infrastructure or legacy.

---

## Scripts

### `scraper.py` ✅ ACTIVE — Stage 1

**What it does:** The Selenium-based web scraper. Reads `metatable-Content.csv` to get target URLs, launches a headless Chrome browser with stealth settings (to bypass government WAFs), extracts the main content region from each page, and saves two output files per page:
- A cleaned `.md` file to `IPFR-Webpages/`
- The raw `.html` DOM to `IPFR-Webpages-html/`

It also saves a per-run CSV report to `scrape_reports/`. This is your entry point to the whole pipeline.

---

### `scripts/process_md_to_json.py` ✅ ACTIVE — Stage 2

**What it does:** The core transformation engine. Takes each `.md` file from `IPFR-Webpages/`, matches it to its row in `metatable-Content.csv`, and builds a fully structured Schema.org JSON-LD file in `json_output/`. This is the most complex script in the repo.

Key internal functions:
- **`parse_markdown()`** — splits the file into blocks by heading, classifies each block as `faq`, `section`, `howto_step`, or `excluded`
- **`match_meta()`** — deterministically links a `.md` file to its CSV row via UDID, URL, or title match
- **`build_jsonld()`** — assembles the full `@graph` document including the `WebPage`, main entity (Article/GovernmentService/Service), `FAQPage`, `WebPageElement` sections, `HowTo` steps, legislation citations, and internal page stubs
- **`_validate_and_repair_jsonld()`** — post-build pass that replaces any placeholder descriptions with auto-generated summaries

Output goes to `json_output/` as `{UDID}_{slug}.json`.

---

### `scripts/json_to_csv.py` ✅ ACTIVE — Stage 5

**What it does:** Flattens the JSON-LD files from `json_output-enriched/` (or `json_output/` if you skip Stage 3) into relational tables and writes them to the target XLSX file. This is the final data normalisation step.

What it populates:
- `ENT_webpage` — one row per page
- `ENT_stakeholder` — organisations found in the graph
- `ENT_website` — the IPFR website entity
- `ENT_external_reference` — outbound links to external sites
- `JUNCT_webpage_links` — resolved internal and external link edges
- `ENT_webpage_main_content` — `WebPageElement` text blocks
- `ENT_webpage_faq` — question/answer pairs
- `ENT_disclaimer` / `JUNCT_disclaimer` — disclaimer text
- `ENT_term` / `JUNCT_webpage_relevant_terms` — IP topic terms

It also handles internal link resolution: it pre-scans all JSON files to build a URL→UDID map, then resolves internal IPFR links to their `webpage_id` rather than treating them as external references. Takes `--json_dir` and `--xlsx_path` as CLI arguments.

---

### `scripts/enrich_howto_steps.py` ⚠️ STAGE 3 — Used only if you run the LLM enrichment step

**What it does:** Walks the JSON tree in `json_output/` looking for placeholder strings (`xXx_PLACEHOLDER_xXx`, `xXx_Err-PLACEHOLDER_xXx`) and replaces them with LLM-generated values via the OpenAI API. It handles four scenarios: HowTo step names, page descriptions, organisation names, and service type classification.

Critically, it includes a **Semantic Diff Guardrail** (`perform_diff_check()`) that rejects any enriched file where the LLM changed something it shouldn't have — only placeholder values are allowed to change. Output goes to `json_output-enriched/` along with an audit report.

**If you are feeding `json_output/` directly into Stage 5 (skipping Stage 3), this script is not needed.** It's only relevant if you're generating content for `json_output-enriched/`.

---

### `scripts/validate_quality.py` ⚠️ STAGE 4 — QA only, not part of core data flow

**What it does:** Compares the enriched JSON files against the source HTML to check for quality issues. Runs five validation layers: JSON structure, schema keys, ID match, semantic text similarity (via `difflib`), FAQ question presence, and link integrity.

Produces `reports/validation_reports/Validation_Report_Extended.csv`. The report you have in the repo (document 20) was generated by this script.

**Not needed if you just want data in the XLSX.** It's a QA/audit tool, not a data transformation step.

---

### `scripts/generate_embeddings.py` ❌ NOT PART OF CORE WORKFLOW

**What it does:** Reads a `sqlite_data/Semantic.xlsx` file and generates OpenAI vector embeddings for each chunk, saving them back to CSV/XLSX/JSON. This is entirely separate from the scrape→JSON→CSV pipeline — it's a downstream enrichment step that adds semantic search capability to the data that's already in the spreadsheet.

**Can be ignored unless you are specifically working on semantic search/RAG features.**

---

### `load_json_output_into_xlsx.py` ❌ SUPERSEDED

**What it does:** An earlier version of the JSON→XLSX loader. It reads JSON files structured around a `@graph` with a different node pattern (looking for `WebPage` nodes with an `identifier` field directly, rather than the nested schema used by the current `process_md_to_json.py` output). It handles `FAQPage`, `WebPageElement`, stakeholders, terms, and link resolution.

**This is effectively a prior iteration of `scripts/json_to_csv.py`.** The current pipeline uses `json_to_csv.py` via `stage5_normalization.yml`. This root-level file appears to be a legacy artefact that can likely be deleted.

The two scripts overlap significantly but differ in:
- `load_json_output_into_xlsx.py` uses `@graph` traversal with `@id` resolution
- `scripts/json_to_csv.py` uses jsonpath-ng and a YAML config (`schema_mapping.yaml`)

## GitHub Actions Workflows

### `.github/workflows/scrape.yml` ✅ ACTIVE — Stage 1

**What it does:** Runs `scraper.py` on a cron schedule (every 6 hours) and on manual dispatch. Sets up Python + Chrome, runs the scraper, then commits any changed files in `IPFR-Webpages/` and `IPFR-Webpages-html/` back to the repo. Only commits if content actually changed.

---

### `.github/workflows/process_json.yml` ✅ ACTIVE — Stage 2

**What it does:** Runs `scripts/process_md_to_json.py` on manual dispatch. Verifies at least one JSON was generated, uploads the `json_output/` folder as a build artifact, and commits the JSON files and the Stage 2 after-action report back to the repo.

---

### `.github/workflows/stage5_normalization.yml` ✅ ACTIVE — Stage 5

**What it does:** Runs `scripts/json_to_csv.py` on manual dispatch. Reads from `json_output-enriched/` (adjust to `json_output/` if you skip Stage 3), outputs to `sqlite_data/`, and auto-commits all CSV/XLSX files using `stefanzweifel/git-auto-commit-action`.

---

### `.github/workflows/enrich_json_action.yml` ⚠️ STAGE 3 — LLM enrichment only

**What it does:** Runs `scripts/enrich_howto_steps.py` on manual dispatch. Requires `OPENAI_API_KEY` as a repo secret. Uploads both the enriched JSON files and the audit CSV as artifacts, and commits them back to the repo. **Only needed if you're running the LLM enrichment step between Stage 2 and Stage 5.**

---

### `.github/workflows/validate-quality.yml` ⚠️ STAGE 4 — QA only

**What it does:** Runs `scripts/validate_quality.py` on manual dispatch. Commits the updated validation report CSV back to the repo if it changed. **Not needed for the data pipeline itself — QA/audit use only.**

---

### `.github/workflows/load-json-output-into-xlsx.yml` ❌ SUPERSEDED

**What it does:** Runs the root-level `load_json_output_into_xlsx.py` (the legacy loader) as a parameterised workflow with inputs for `json_dir`, `xlsx_path`, and whether to commit. **This is the workflow for the superseded script — it can be deleted along with `load_json_output_into_xlsx.py`.**

---

### `.github/workflows/create_embeddings.yml` ❌ NOT PART OF CORE WORKFLOW

**What it does:** Runs `scripts/generate_embeddings.py` on manual dispatch. Reads `sqlite_data/Semantic.xlsx`, calls the OpenAI Embeddings API, and saves the output as CSV/XLSX/JSON. **Only relevant for the semantic search/RAG use case downstream of the core pipeline.**

---

## Configuration & Data Files

### `metatable-Content.csv` ✅ ACTIVE — Control Plane

**What it does:** The single source of truth for the entire pipeline. Every page in the IPFR system has a row here. Fields used actively by the pipeline:

| Field | Used by |
|---|---|
| `UDID` | Filename generation, JSON `identifier`, CSV primary key |
| `Main-title` | JSON `headline`, file matching |
| `Canonical-url` | Scraper target, JSON `url`, file matching |
| `Archectype` | Determines JSON `@type` (Article / GovernmentService / Service) |
| `Relevant-ip-right` | Drives `about` topics, legislation citations, topic map |
| `Provider` | Populates service operator / provider organisation entity |
| `Publication-date` / `Last-updated` | JSON date fields |
| `Additional-disclaimer` | Injected as a `WebPageElement` disclaimer section |
| `Keywords` | JSON `keywords` array on the WebPage |
| `Overtitle` | Used in file matching heuristics |

---

### `scripts/schema_mapping.yaml` ⚠️ STAGE 5 CONFIG — Check if still used

**What it does:** A YAML config that defines table structures and jsonpath-ng extraction rules for the Stage 5 normalisation step. Maps JSON-LD paths to spreadsheet columns for each output table (Primary, LinksTo, HowTo, FAQ, Semantic, RawData).

However, looking at `scripts/json_to_csv.py`, **this YAML file does not appear to be loaded or used by the current version of `json_to_csv.py`**. The current script uses hardcoded logic rather than reading from the YAML config. The YAML may be a design artefact from an earlier iteration. Worth verifying whether it's referenced anywhere before deleting it.

---

### `requirements.txt` ✅ ACTIVE

Lists all Python dependencies used across the pipeline: `selenium`, `selenium-stealth`, `markdownify`, `beautifulsoup4`, `pandas`, `openpyxl`, `tiktoken`, `jsonpath-ng`, `pyyaml`, `markdown`, etc.

---

### `after_action_report.csv` ⚠️ STAGE 3 OUTPUT — Generated artefact

The LLM enrichment audit log produced by `enrich_howto_steps.py`. Records every placeholder replacement made, the context sent to the LLM, the generated value, and the diff check result. **Not an input to anything — it's an output/log file.**
